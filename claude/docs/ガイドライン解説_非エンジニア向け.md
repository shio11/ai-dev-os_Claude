# Claude に渡している「開発ルール」のやさしい解説

このメモは、`~/.claude/CLAUDE.md` と、そこから読むように指定しているルール集（ガイドライン）の中身を、プログラミングに詳しくない人向けに説明したものです。
ルールそのものを変えるものではなく、「何のためのルールで、Claude が実際にどう振る舞うか」を理解するための読みものです。

---

## 0. まず全体像

### CLAUDE.md とは
Claude Code が作業を始めるときに必ず最初に読む「作業指示書」です。新しく現場に来た職人さんに渡す「この家ではこういう決まりで作業してください」という申し送りメモにあたります。
`~/.claude/`（ホームフォルダ直下の `.claude`）に置いてあるので、**どのプロジェクトで作業するときも共通で**読まれます。

### AI DEV OS とは
公開されている「AI にコードを書かせるときのルール集」です。4段の棚のように整理されています。

| 段 | 名前 | 中身 | たとえ |
|---|---|---|---|
| 1 | 01_philosophy（哲学） | 何を大事にするか | 会社の理念 |
| 2 | 02_decision-criteria（判断基準） | 迷ったときの考え方 | 行動指針 |
| 3 | 03_guidelines/common（共通ルール） | どの開発にも使う具体的な決まり | 全社共通の作業手順書 |
| 4 | 03_guidelines/frameworks（個別ルール） | 特定の種類のアプリ向けの決まり | 部署ごとの作業手順書 |

このうち Claude に読ませているのは、具体的な 3・4 段目の一部と、利用者自身が書き足した追加ルール（project-specific）です。

### ルールがぶつかったときの優先順位
CLAUDE.md には「より具体的なルールが勝つ」という順位が書いてあります。

1. 個別ルール（frameworks）… いちばん強い
2. 共通ルール（common）
3. このPC・このプロジェクト向けの追加ルール（project-specific）
4. 判断基準
5. 哲学 … いちばん弱い（人間どうしの意識合わせ用）

**たとえ:** 「全社ルールでは書類は黒ペン、でも経理部では赤ペン」と決まっていたら、経理部の人は赤ペンを使う。より狭い範囲に向けた決まりのほうが、その場面をよく知っているからです。

### 実際に読ませているファイル（9本）

| 言語 | ファイル | ひとことで |
|---|---|---|
| Python | common/security.md | 安全のルール |
| Python | common/validation.md | 入ってくるデータを確かめるルール |
| Python | frameworks/python-cli/project-structure.md | ファイルとフォルダの整理のしかた |
| Python | project-specific/python-windows.md | Windows で困らないための追加ルール |
| JavaScript | common/security.md | 画面（ブラウザ）側の安全ルール |
| JavaScript | common/validation.md | 画面側でデータを確かめるルール |
| JavaScript | frameworks/browser/project-structure.md | Python アプリの「画面」の作り方 |
| JavaScript | frameworks/nodejs-cli/project-structure.md | Node.js で動く道具の作り方 |
| JavaScript | frameworks/medini/project-structure.md | medini analyze 用スクリプトの書き方 |

JavaScript の個別ルール3本は「どれか1つ」を、作るものの種類に合わせて選んで使います。

> 補足: CLAUDE.md の中で行頭が `#` になっている行（error-handling.md、code.md、naming.md など）は「メモとして残してあるが、今は読ませていない」ものです。

## 1. Python のルール

### 1-1. 安全のルール（common/security.md）

**何のため？**
大事な情報が漏れたり、他人に勝手に操作されたりするのを防ぐためです。
元の文書はインターネットに公開する Web サービス向けに書かれているので、ログイン、決済、個人情報保護法（GDPR）など、手元の PC で使う道具には関係しない項目も多く含まれます。Claude は関係のある部分だけを当てはめます。

**Claude が実際にすること（手元のツールでも効く主なもの）**

- **パスワードや API キー（サービスの合鍵）をプログラムに直接書かない。**
  `.env` という別ファイルや環境変数（PC に登録しておく設定値）から読み込むようにし、Git（変更履歴の保管庫）には入れません。
- **外から来るものはすべて「まず疑う」。**（ゼロトラストという考え方）
  ファイルの中身、入力された文字、ネットから取った情報は、確かめてから使います。
- **必要な権限だけを渡す。**（最小権限）
- **エラーが起きても、画面に内部の詳しい情報（プログラムの内部の行番号の一覧＝スタックトレース など）をそのまま出さない。** 攻撃のヒントになるためです。
- **新しく部品（ライブラリ）を足すとき、ライセンスを確認する。** MIT・Apache など自由に使えるものは OK、GPL・AGPL など「自分のコードも公開する義務」が生じうるものは使いません。
- **外から取り込んだ HTML や文章を画面に出すときは、無害化（サニタイズ）する。**

**Web サービスを作るときだけ効くもの（参考）**
- 他人のデータを見られないようにする確認（「このデータの持ち主は本人か」を毎回チェック。IDOR 対策）
- ログイン試行の回数制限（総当たり攻撃対策）
- 外部サービスからの通知（Webhook）が本物かどうかの署名チェック
- HTTPS の強制、Cookie の設定、管理画面の IP 制限、メンテナンスモード など

**身近なたとえ**
- 家の合鍵を玄関マットの下（＝プログラムの中）に置かず、金庫（＝別ファイル）にしまう。
- 宅配便を受け取るとき、差出人と中身を確かめてから開ける。
- 銀行の窓口で「エラーです」とは言っても、金庫の暗証番号の仕組みまでは説明しない。

### 1-2. データを確かめるルール（common/validation.md）

**何のため？**
おかしなデータが紛れ込んで、計算ミスや異常な動作が起きるのを入り口で止めるためです。

**Claude が実際にすること**
- データの「型」（文字か数字か、日付か など）と「範囲」を、**Pydantic** という確認用の道具でまとめて定義します。
- 数字の範囲（例: 数量は 1〜999、割引は 0〜100%）、日付の前後関係（終了日は開始日より後）、条件付きの必須項目（支払い方法が「カード」ならカード番号が必須）などを、その定義の中に書きます。
- 逆に、「すでに登録済みか」のようにデータベースを見ないと分からない確認は、そこには書かず別の場所で行います。
- 「入力の決まり」「保存先（データベース）の決まり」それぞれに、**正解の置き場所を1か所に決める**ことで、あちこちで食い違うのを防ぎます。

**身近なたとえ**
役所の申請書の受付窓口。記入漏れや「生年月日が未来になっている」ような明らかな誤りは、窓口でその場で突き返します。一方で「この人は本当に住民登録があるか」は、奥の台帳を調べないと分からないので担当部署が確認します。
書類の様式（どの欄に何を書くか）は1つの正式な様式に決めておき、部署ごとに勝手な様式を作らせません。

> このルールも元は Web サービス（データベースあり）を想定しているため、データベースを使わないツールでは「Pydantic などで入力を確かめる」部分が中心になります。

### 1-3. ファイルとフォルダの整理のしかた（frameworks/python-cli/project-structure.md）

**何のため？**
プログラムが大きくなっても、どこに何があるか分かり、1か所の修正が思わぬ場所を壊さないようにするためです。

**Claude が実際にすること**
- **機能ごとにフォルダを分ける。**（例: 「集める」「加工する」「報告を作る」をそれぞれ別のフォルダに）
- **「受付係」と「実務担当」を分ける。** 起動のときに指示を受け取る部分（cli）は、指示を受け取って実務担当に渡すだけにし、計算や判断などの中身は書きません。こうすると中身の部分を、ほかのプログラムからも部品として使えます。
- **部署どうしを直接つながない。** 共通で使う処理は「共有の道具箱」（utils）に移し、機能フォルダどうしが直接呼び合わないようにします。道具箱から機能フォルダを呼ぶのも禁止です。ぐるぐる回る依存（循環）も作りません。
- **テストもプログラムと同じ並びで整理する。** 小さな部品のテスト、組み合わせのテスト、実際に起動して確かめるテスト（E2E）に分けます。

**身近なたとえ**
レストランの厨房とホール。ホール係（cli）は注文を聞いて厨房に伝えるだけで、料理はしません。厨房は「前菜」「メイン」「デザート」と持ち場が分かれ、塩や包丁などの共有品は共用の棚（utils）に置きます。メイン担当が前菜担当の冷蔵庫を勝手に開けないので、どこかの持ち場を作り直しても他に影響しません。

### 1-4. Windows で困らないための追加ルール（project-specific/python-windows.md）

これは利用者自身が書いた、このPCの環境に合わせたルールです。ai-dev-os のルールとぶつかった場合は ai-dev-os 側が優先です。

**ファイルとパス**
- **ファイルを読み書きするときは、文字コード（文字の記録方式）を必ず指定する。** 基本は `utf-8`、Excel で開く CSV は `utf-8-sig`、.bat ファイルは `cp932`。
  - 何のため？ Windows は指定しないと古い方式（cp932）で読むため、日本語が文字化けしたりエラーになったりします。
  - たとえ: 手紙を送るとき「これは日本語で書いてあります」と封筒に書いておく。書いていないと相手が別の言語だと思って読めなくなる。
- **ファイルの場所（パス）は、文字をつなぎ合わせて作らず、専用の道具（`pathlib`）で組み立てる。**
  - 何のため？ `\` と `/` の違いや区切りの付け忘れで、存在しない場所を指してしまうのを防ぐため。
  - たとえ: 住所を手書きでつなげるのではなく、郵便番号から住所を自動で出してくれる機能を使う。

**エラー**
- **利用者に見せるエラーには「どのファイルの、何が原因か」を書く。**
  - たとえ: 「書類に不備があります」ではなく「申請書の3行目、生年月日の欄が空です」と伝える。

**部品（クラス）の設計**
- **「〜の一種」という関係がはっきりしない限り、親子関係（継承）ではなく組み合わせ（コンポジション）で作る。**
  - たとえ: 「車」を作るとき「エンジンの子ども」とはせず、「エンジンを積んでいる」と考える。後でエンジンを取り替えやすい。
- **変えなくてよい値は「変更不可」にしておく。**（`@dataclass(frozen=True)`）
  - たとえ: 完成した書類は清書してハンコを押し、あとから書き換えられないようにする。
- **壊されると困る値は、外から直接いじれないようにする。** ただし、値を入れておくだけの簡単な入れ物には、わざわざ手続き（getter/setter）を書かない。
  - たとえ: 金庫の中身は担当者経由でしか出し入れさせないが、文房具の引き出しにまで鍵はかけない。

**起動のしかた**
- 利用者が起動するファイルは、アプリのフォルダのすぐ下にある `main.py` にし、そこで `uv run main.py`（または `python main.py`）で起動できるようにする。
- `main.py` には中身を書かず、本体（`src` フォルダの中）を呼び出すだけにする。
- 上のフォルダに共有の実行環境（`.venv`）がある場合は、アプリごとに別の環境を作らせない設定を入れる。
- 何のため？ 起動方法が毎回同じになり、「どこで何を打てば動くのか」で迷わないため。
- たとえ: どの家電もコンセントの差し込み口は同じ形にしておく。中の仕組みが違っても、使う人は同じやり方で電源を入れられる。

## 2. JavaScript のルール

JavaScript は主に「画面」（ブラウザで見る部分）や、小さな道具を作るのに使います。

### 2-1. 画面側の安全ルール（common/security.md）

**何のため？**
ブラウザに表示した画面を悪用されたり、秘密情報が見えてしまったりするのを防ぐためです。ブラウザの中身は利用者がいつでも覗いたり書き換えたりできる、という前提に立ちます。

**Claude が実際にすること**
- **画面のプログラム（JS・HTML）にパスワードや API キーを書かない。** 誰でも見られるからです。
- **外から来た文字を画面に出すときは「ただの文字」として出す。** HTML として解釈させる書き方（`innerHTML` など）に外部の文字を渡しません。AI が作った文章を表示するときも同じです。
  - 何のため？ 文字の中に悪い命令が仕込まれていると、それが実行されてしまう（XSS という攻撃）ため。
- **文字列を「プログラムとして実行する」機能（`eval` など）を使わない。**
- **Python から画面にデータを渡すときは、決まった安全な形（JSON という形式）で渡す。** プログラムの文章の中に値を直接埋め込みません。
- **ブラウザの保存領域には、列の幅など「見た目の好み」だけを保存する。** 個人情報や業務データは入れません。
- **外部の部品はネット（CDN）から読み込まず、手元に保存し、バージョンを明記する。** 追加する前に目的・ライセンス・大きさを示して相談します。
- **画面に内部のエラー情報やフォルダの場所を出さない。**
- Node.js の道具では、受け取ったファイルの場所が「許可したフォルダの外」を指していないか確かめる（パストラバーサル対策）、命令の組み立てを文字のつなぎ合わせで行わない、なども守ります。

**身近なたとえ**
- お店のショーウィンドウ（＝ブラウザ）に、金庫の暗証番号のメモを貼らない。
- お客さんから届いた手紙を掲示板に貼るとき、「中の指示に従う」のではなく「文面を見せるだけ」にする。
- 業務の材料は信頼できる問屋から仕入れて倉庫に保管し、毎回よく知らない露店から買わない。

### 2-2. 画面側でデータを確かめるルール（common/validation.md）

**何のため？**
画面に変なデータが入って表示が壊れたり、誤った値で操作が進んだりするのを防ぐためです。

**Claude が実際にすること**
- **業務上の正しさの最終判断は Python 側。** 画面側の確認は「入力した瞬間に間違いを知らせる」ためと、「画面が壊れないようにする」ためだけです。
- **外から画面に入ってくるデータ（サーバーからの返事、入力欄、URL など）は、入ってきた場所ですぐ確かめる。** 確かめていないデータを表示部分に渡しません。
- 「重複していないか」「在庫があるか」など、画面が知らない情報が要る確認は Python に任せます。
- 同じ決まりが Python と画面の両方にあるときは、上限値などを同じ名前の定数にし、両者が一致しているかを確かめるテストを付けます。
- 日付だけの値（例: `2026-11-16`）は、時刻つきの日付に変換しない。変換すると時差で日付が1日ずれることがあるためです。

**身近なたとえ**
コンビニのレジで、明らかに桁がおかしい金額を打つと「確認してください」と出る（画面側の確認）。でも、カードの残高が足りるかを決めるのはカード会社（Python 側）です。

### 2-3. Python アプリの「画面」の作り方（frameworks/browser/project-structure.md）

Python で起動するアプリに、ブラウザで見る画面を付けるときのルールです。

**何のため？**
Node.js などの追加ソフトがなくても、会社の PC の Edge / Chrome でそのまま動く、整理された画面を作るためです。

**Claude が実際にすること**
- **最初に「読み込み方式」を決めて、理由を書く。** Python がサーバーとして配信するのか、Python が作った1枚の HTML ファイルを直接開くのかで、書き方が変わります。既存のやり方があればそれに合わせます。
- **役割ごとにファイルを分ける。**
  - `app.js` … 入口（準備だけ）
  - `api.js` … Python とのやりとりの唯一の窓口
  - `types.js` … データの形の定義
  - `lib.js` … 計算・整形などの小道具
  - `views.js` … 画面の部品を作る・書き換える
  - 呼び出す向きは一方通行にします。
- **計算や判定などの業務の中身は Python に置き、画面には書かない。**（Python がいない「ファイルを直接開く方式」だけは例外）
- **エラーは画面にちゃんと表示する。** 開発者向けの記録（console）だけで済ませません。通信には時間切れ（タイムアウト）を付けます。
- **既存のファイルを直すときは、直す場所だけをルールに合わせ、周りの書き方に合わせる。** ルールに合わせることだけが目的の書き換えはせず、必要なら提案して了承をもらってから行います。
- 画面の動作確認は、Python のテストからブラウザを動かして行います。

**身近なたとえ**
お店のレイアウト。受付（app）、電話窓口（api）、商品台帳（types）、作業台（lib）、陳列棚（views）を分けておくと、陳列を変えても電話窓口には影響しない。値段を決めるのは本部（Python）で、店頭では決めない。

### 2-4. Node.js で動く道具の作り方（frameworks/nodejs-cli/project-structure.md）

**何のため？**
Node.js（JavaScript を PC 上で動かす仕組み）でコマンド型の道具を作るとき、整理された形にするためです。

**Claude が実際にすること**
中身は 1-3（Python の整理のしかた）とほぼ同じ考え方です。
- 機能ごとにフォルダを分ける。
- 起動時に指示を受ける部分（cli）は受付だけ。中身は書かない。
- 機能フォルダどうしを直接つながず、共通処理は道具箱（utils）へ。
- 違いは、テストを部品のすぐ隣に置く（`○○.test.js`）ことです。

**身近なたとえ**
1-3 のレストランの厨房と同じです。違いは「各持ち場に、その料理の味見メモを一緒に置いておく」くらいです。

### 2-5. medini analyze 用スクリプトの書き方（frameworks/medini/project-structure.md）

medini analyze（機能安全の分析ツール）の中で動かす小さなプログラムのルールです。このルールは他の JavaScript のルールより優先されます。

**何のため？**
medini の中の JavaScript は古い仕組み（Rhino）で動くため、新しい書き方が使えるか確認できていません。また、分析データを書き換えるので、途中で失敗して中途半端なデータが残るのを防ぐ必要があります。

**Claude が実際にすること**
- **確実に動く古い書き方だけを使う。** 新しい書き方（`let`、`const`、矢印の関数など）は使いません。
- **1つのスクリプトは1つのファイルで完結させる。** 共通処理は各ファイルにコピーし「(○○.js と同じ)」と注記します。
- **スクリプトを作ったら、必ず解説書（docs）もセットで作る。** 処理を小さな段階に分け、プログラミングに詳しくない人向けの日本語で説明します。
- **ファイルの先頭に、目的・入力する CSV の形・根拠となるマニュアルの章・実機で確認したこと／していないこと（日付つき）・使い方を書く。**
- **「試し運転モード」（`DRY_RUN`）を付ける。** 書き込まずに、何が起きるかだけを確認できます。
- **処理の順番を決めておく。** 選択の確認 → ファイル選択 → CSV 読み込み → **書き込む前に全体をチェックし、1件でも問題があれば書き込まない** → （試し運転なら結果を見せて終了）→ 書き込み → 件数と次の操作を表示。
- **項目名を推測で書かない。** 分からなければ実機で調べ、その日付を記録します。
- **途中で問題が起きたらわざと止める。** medini は途中で止まるとそのスクリプトでの変更をすべて取り消すので、中途半端な書き込みを防げます。
- 個人のフォルダの場所などはスクリプトに書かず、`C:\work\...` のような汎用の場所にします。

**身近なたとえ**
- 大事な書類に記入する前に、まず鉛筆で下書き（試し運転）して確認し、問題がなければペンで清書する。
- 銀行の振込は、全件の内容を先にチェックし、1件でもおかしければ全部送らない。途中で止まったら全部なかったことにする。
- 機械の操作マニュアルの表紙に「対応機種・確認日・使い方」を必ず書いておく。

## 3. 用語の小辞典

| 用語 | 意味 |
|---|---|
| API キー | 外部サービスを使うための合鍵となる文字列 |
| 環境変数 / `.env` | パスワードなどをプログラムの外に置いておく場所 |
| Git | ファイルの変更履歴を残す仕組み |
| ライブラリ | 他の人が作った、組み込んで使える部品 |
| ライセンス | 部品を使うときの約束事（自由に使える／公開義務がある など） |
| 検証（バリデーション） | データが正しい形・範囲か確かめること |
| Pydantic | Python でデータの形と決まりをまとめて定義・確認する道具 |
| 文字コード | 文字をコンピューターに記録する方式（utf-8、cp932 など） |
| パス | ファイルやフォルダの場所を示す住所 |
| クラス / 継承 / コンポジション | プログラムの部品の設計図／親子関係で作る方法／組み合わせで作る方法 |
| CLI | 文字のコマンドで操作する道具 |
| XSS | 画面に悪い命令を紛れ込ませる攻撃 |
| CDN | ネット上の部品配布場所 |
| テスト / E2E | 正しく動くか確かめるプログラム／実際に起動して最初から最後まで確かめるテスト |
| DRY_RUN | 実際には書き込まずに結果だけ確かめる試し運転 |
