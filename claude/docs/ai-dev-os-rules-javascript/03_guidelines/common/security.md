# Security Guidelines

This document defines security rules for browser JavaScript served or generated by a local / internal Python app (sections 1–8) and for Node.js tools (section 9). Server-side rules of the Python app (authentication, authorization, CSRF, headers) belong to the Python guidelines.

## 1. Fundamental Principles

* Treat every value from outside the code as untrusted: API responses, embedded JSON, form input, URL, `localStorage`, file contents, clipboard.
* The browser is not a trust boundary — anything in JS or HTML is visible and editable by the user. MUST NOT rely on JS checks for permissions or data integrity.
* MUST NOT put secrets (API keys, passwords, tokens, internal hostnames that must stay private) in JS, HTML, or embedded JSON.

## 2. XSS Prevention (DOM)

* MUST insert text with `textContent` or `createElement`; MUST NOT pass untrusted data to `innerHTML`, `outerHTML`, `insertAdjacentHTML`, or `document.write`.
* `innerHTML` is allowed only for fixed template strings that contain no external data.
* MUST NOT build URLs for `href` / `src` from untrusted data without checking the scheme is `http:` / `https:` (block `javascript:`).
* MUST NOT use `eval`, `new Function`, or string arguments to `setTimeout` / `setInterval`.
* MUST NOT use inline event attributes (`onclick="..."`); register with `addEventListener` (keeps CSP without `'unsafe-inline'` possible).

## 3. Data Embedded by Python

* Embedded data MUST use `<script type="application/json" id="...">` and be read with `JSON.parse(element.textContent)`.
* Python MUST escape `<` before embedding: `json.dumps(data, ensure_ascii=False).replace("<", "\\u003c")`.
* Python MUST NOT interpolate values into JavaScript source (`f"const data = {value};"`).

## 4. Storage

* `localStorage` / `sessionStorage` are for UI preferences only (column widths, last filter). MUST NOT store personal data, credentials, or business data that must stay consistent with Python.
* Values read from storage MUST be validated like any other untrusted input.

## 5. External Libraries

* MUST vendor libraries under `static/lib/` with the version in the file name; MUST NOT load from CDNs.
* Before adding a library, state purpose, license, and size, and get approval.
* **Permitted licenses**: MIT, Apache-2.0, ISC, BSD variants, CC0, Unlicense, MPL-2.0. **Prohibited**: AGPL, GPL-2.0, GPL-3.0.
* Check the vendored version for known vulnerabilities when adding or updating it.

## 6. Communication

* Call only the Python app's own origin (relative paths in `api.js`). Calls to other origins need explicit approval.
* State-changing calls use `POST` / `PUT` / `PATCH` / `DELETE`, never `GET`.

## 7. Information Leakage

* MUST NOT show stack traces or internal paths on screen.
* `console` output MUST NOT include personal data or full API payloads in shipped code.

## 8. AI / LLM Content

* When the screen displays text produced by an LLM or fetched from outside, render it as text (`textContent`), never as HTML.

## 9. Node.js Tools

* Secrets come from environment variables or an untracked config file; MUST NOT be committed or printed.
* **Path traversal**: any path received from arguments, config, or external input MUST be resolved and checked against an allowed base directory before use:

```js
/** @param {string} inputPath @param {string} allowedBase @returns {string} */
export function validatePath(inputPath, allowedBase) {
  const resolved = path.resolve(inputPath);
  const base = path.resolve(allowedBase);
  if (resolved !== base && !resolved.startsWith(base + path.sep)) throw new Error(`Path traversal detected: ${inputPath}`);
  return resolved;
}
```

* MUST NOT build shell commands from strings; use `execFile` / `spawn` with an argument array.
* External content passed to an LLM (web pages, files, API responses) is untrusted data, never instructions; strip hidden markup and redact secrets first.
* Pin exact versions of dependencies; run `npm audit` when adding or updating packages. License policy is the same as section 5.
